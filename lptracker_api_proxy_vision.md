# Vision сервиса: совместимый API-прокси над LPTracker

**Версия:** 1.0\
**Статус:** Vision / концепция MVP\
**Назначение документа:** зафиксировать цели, концепцию, принципы и
границы MVP для разработчика. Документ задаёт направление реализации, но
не заменяет техническое задание и спецификацию API.

------------------------------------------------------------------------

## 1. Краткое описание

Разработать мультиарендный API-сервис, который предоставляет клиентам
интерфейс, максимально совместимый с LPTracker API, при этом скрывает от
них использование LPTracker как внутренней системы.

Клиент подключается к endpoint'ам нашего сервиса и использует выданные
нами credentials. Запросы обрабатываются от имени одного из
принадлежащих нам LPTracker-аккаунтов. Клиент не получает доступ к
LPTracker credentials, токенам или внутренней инфраструктуре.

**Ключевая идея:** для клиентской системы наш сервис выглядит как
LPTracker API, но точкой подключения и контроля доступа является наша
платформа.

## 2. Цель и ценность

### Цель MVP

Обеспечить клиентам возможность интегрироваться с LPTracker через наш
сервис с минимальными изменениями в их интеграционном коде --- в идеале,
заменив только базовый URL и данные авторизации.

### Ценность

-   Скрыть от клиента прямую зависимость от LPTracker и его внутренние
    credentials.
-   Централизовать подключение клиентов к нашим LPTracker-аккаунтам.
-   Управлять доступом каждого клиента независимо.
-   Контролировать и наблюдать за запросами, ошибками и нагрузкой.
-   Сохранить возможность развивать собственный API-слой в дальнейшем
    без обязательного изменения клиентских интеграций.

## 3. Пользователи и модель обслуживания

Сервис предназначен для нескольких независимых клиентов (multi-tenant).

Каждый клиент получает от владельца сервиса: - базовый URL / endpoint
сервиса; - credentials для авторизации в нашем API; - документацию по
поддерживаемому совместимому API.

Владелец сервиса самостоятельно создаёт и настраивает клиентские
подключения, назначает клиентам доступные LPTracker-контексты и выдаёт
credentials. Самостоятельный onboarding клиентов через пользовательский
интерфейс в MVP не требуется.

## 4. Концептуальная схема

``` text
Клиент A ─┐
Клиент B ─┼──► Наш API-сервис ───► LPTracker API
Клиент C ─┘          │
                     ├── аутентификация клиента
                     ├── определение tenant и его контекста
                     ├── контроль доступа и изоляция
                     ├── управление LPTracker credentials/token
                     └── журналирование и контроль нагрузки
```

Один сервис обслуживает множество tenants. Разные tenants могут быть
привязаны к одному LPTracker-аккаунту либо к разным аккаунтам. Такая
привязка является внутренней конфигурацией и не раскрывается клиенту.

## 5. Основные архитектурные принципы

### 5.1 Совместимость с LPTracker API

Сервис должен максимально точно воспроизводить поведение поддерживаемой
части LPTracker API: - маршруты и методы; - формат и семантику
запросов; - структуру успешных ответов; - формат и смысл ошибок; -
поведение авторизации --- в той мере, в какой это необходимо для
совместимости и безопасного использования нашего сервиса.

Совместимость должна быть подтверждена тестами. Нельзя заявлять полную
совместимость со всем LPTracker API, пока не определён и не проверен
перечень поддерживаемых методов.

### 5.2 Наш сервис --- единственная публичная точка доступа

Клиент обращается только к нашему домену. LPTracker endpoint'ы,
credentials и токены не передаются клиенту и не должны попадать в ответы
или обычные логи.

### 5.3 Изоляция tenants

Каждый запрос должен быть связан с аутентифицированным tenant. Сервис
самостоятельно определяет разрешённый LPTracker-контекст. Клиент не
должен иметь возможность подменить tenant, аккаунт или проект через
параметры запроса и получить доступ к чужим данным.

### 5.4 Разделение публичного и внутреннего контуров авторизации

Credentials клиента для нашего API и credentials/token LPTracker ---
разные сущности. Секреты LPTracker хранятся и используются только внутри
сервиса. Клиентские credentials должны иметь возможность независимого
отзыва и ротации.

### 5.5 Минимальное вмешательство в бизнес-семантику

Сервис не должен без необходимости менять бизнес-смысл запросов и
ответов LPTracker. Допускаются технические преобразования, необходимые
для авторизации, tenant isolation, совместимости, защиты и устойчивой
работы.

### 5.6 Расширяемость без преждевременного усложнения

В MVP реализуется только LPTracker как backend. При этом публичный слой
и внутренняя интеграция должны быть разделены настолько, чтобы будущая
эволюция не требовала переписывать всю систему. Разработка поддержки
других CRM, универсального интеграционного конструктора или абстрактной
платформы в MVP не требуется.

## 6. Концептуальные компоненты

1.  **Публичный API Gateway / Proxy** --- принимает клиентские запросы и
    возвращает ответы в совместимом формате.
2.  **Client Authentication** --- проверяет credentials, выданные
    клиенту нашим сервисом.
3.  **Tenant / Access Context** --- определяет клиента, его разрешения и
    закреплённый LPTracker-контекст.
4.  **LPTracker Adapter / Proxy Layer** --- передаёт разрешённые запросы
    во внешний API LPTracker и возвращает результаты.
5.  **Credential & Token Management** --- безопасно хранит внутренние
    секреты и обеспечивает актуальность LPTracker-авторизации.
6.  **Operational Controls** --- ограничение нагрузки, обработка
    технических сбоев, журналирование и мониторинг.

Это концептуальное разделение ответственности, а не предписание
конкретных технологий или физического развертывания.

## 7. Безопасность и доверительные границы

Безопасность является обязательным свойством MVP, а не последующим
улучшением.

-   Внешний доступ осуществляется по HTTPS.
-   LPTracker credentials и токены никогда не возвращаются клиенту.
-   Секреты не записываются в открытом виде в логи.
-   Клиентские credentials должны быть индивидуальными, отзывными и
    ротируемыми.
-   Доступ к данным определяется серверной конфигурацией tenant, а не
    доверенными параметрами запроса клиента.
-   Ошибки и диагностические ответы не должны раскрывать секреты,
    внутренние URL или конфигурацию других tenants.
-   Должны быть предусмотрены защита от чрезмерной нагрузки и базовые
    меры против злоупотребления API.

## 8. Устойчивость и эксплуатация

Сервис должен корректно обрабатывать недоступность LPTracker, ошибки
авторизации, ограничения частоты запросов и некорректные ответы
upstream-системы.

Повторные запросы допустимы только там, где это безопасно с учётом
семантики операции. Нельзя автоматически повторять потенциально
изменяющие данные операции без оценки риска дублирования.

Логи и мониторинг должны позволять установить: - какой tenant выполнил
запрос; - когда и к какому типу операции он относился; - результат и
класс ошибки; - длительность обработки; - факт ограничения нагрузки или
сбоя upstream.

Логирование не должно сохранять секреты и избыточные персональные
данные.

## 9. Границы MVP

### Входит в MVP

-   Один backend-провайдер: LPTracker.
-   Мультиарендная модель.
-   Выдача credentials клиентам владельцем сервиса.
-   Привязка tenants к одному или нескольким LPTracker-контекстам по
    конфигурации владельца.
-   Совместимое проксирование согласованного перечня LPTracker
    API-методов.
-   Внутреннее управление LPTracker credentials и токенами.
-   Контроль доступа и изоляция tenants.
-   Обработка ошибок, базовое ограничение нагрузки, логирование и
    мониторинг.
-   Тесты совместимости для согласованного набора API-методов.

### Не входит в MVP

-   Собственная CRM или бизнес-логика обработки лидов.
-   Поддержка других CRM или backend-провайдеров.
-   Клиентский self-service кабинет и самостоятельная регистрация.
-   Биллинг, тарифы и marketplace.
-   Визуальный конструктор интеграций.
-   Собственная нормализованная модель данных CRM.
-   Аналитическая платформа для клиентов.
-   Полная замена LPTracker.

## 10. Критерии успеха MVP

MVP можно считать достигшим цели, если:

1.  Клиент может выполнять согласованные операции LPTracker API через
    наш endpoint.
2.  Для подключения клиент использует credentials нашего сервиса, а не
    LPTracker.
3.  LPTracker credentials и токены не раскрываются клиенту.
4.  Запросы одного tenant не дают доступа к данным или контексту другого
    tenant.
5.  Поведение поддерживаемых методов проверено тестами на совместимость
    с LPTracker.
6.  Владелец сервиса может выдать, ограничить, отозвать и заменить
    клиентские credentials без передачи клиенту внутренних секретов
    LPTracker.
7.  Сбои и ошибки можно диагностировать по логам и метрикам без
    раскрытия секретов.

## 11. Что разработчик должен уточнить до реализации

Этот документ намеренно не фиксирует детали, которые требуют отдельного
согласования. До начала разработки необходимо определить:

-   точный перечень LPTracker API-методов, входящих в MVP;
-   требования к совместимости авторизации и форматов ошибок;
-   правила распределения клиентов по LPTracker-аккаунтам и проектам;
-   лимиты запросов и поведение при достижении ограничений LPTracker;
-   способ административной настройки tenants и credentials;
-   требования к хранению секретов, резервному копированию и срокам
    хранения логов;
-   среду развертывания, домен, TLS и процедуру выпуска/отзыва
    credentials.

Разработчик должен зафиксировать эти решения в технической спецификации
до реализации соответствующих компонентов.

## 12. Итоговая формулировка Vision

> Сервис --- это мультиарендный API Gateway/Proxy, предоставляющий
> клиентам совместимый с согласованной частью LPTracker API интерфейс.
> Клиенты аутентифицируются исключительно в нашем сервисе. Сервис
> самостоятельно определяет tenant и разрешённый LPTracker-контекст,
> выполняет запросы от имени владельца сервиса и скрывает от клиентов
> LPTracker credentials, токены и внутреннюю инфраструктуру. MVP
> фокусируется на безопасном, наблюдаемом и максимально совместимом
> проксировании LPTracker API без добавления собственной CRM-логики.
