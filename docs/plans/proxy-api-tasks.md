# ProxyAPI: задачи с обязательным подтверждением готовности

Приложение к [плану](proxy-api-implementation-plan.md). Версия: 22.09.2026. Объём: весь [реестр API](proxy-api-endpoint-inventory.md), один проект на клиента из ручного конфига, собственная авторизация. Это рабочая последовательность для команды среднего уровня.

## Как выполнять

1. Заказчик назначает принимающего: технического руководителя/reviewer; для продукта и спорного изменения контракта — самого заказчика. Разработчик не принимает свою задачу самостоятельно.
2. Начинать с 0.1. По умолчанию следующая задача по списку заблокирована до письменной отметки «Принято» у предыдущей. Также должны быть приняты указанные зависимости этапа из основного плана.
3. Одна задача — один небольшой PR или отдельный исследовательский отчёт. Не объединять несколько ещё не принятых задач в большой PR. Если задача разрастается, сначала согласовать её разбиение с отдельными результатами и критериями приёмки.
4. После выполнения передать комплект на проверку и установить «На проверке». Продолжать можно исправления текущей задачи и ответы reviewer; следующую реализацию до подтверждения не начинать.
5. Проверяющий принимает задачу либо возвращает конкретные замечания. После исправлений — повторная проверка. Успешный CI, merge без review и молчание не считаются подтверждением.
6. Последняя задача этапа дополнительно закрывает его контрольную точку G0–G8. Следующий этап открывается после отдельного подтверждения этой точки.
7. Параллельная работа возможна только по явно согласованным веткам: reviewer записывает ID разрешённых задач и подтверждает принятые зависимости. Это не отменяет приёмку каждой задачи.

Статусы: **Не начата → В работе → На проверке → Принята**. При замечаниях: **На проверке → Доработка → На проверке**. При внешнем ограничении: **Заблокирована**, с конкретным фактом и решением, которое нужно получить. Сейчас все задачи «Не начата»; подготовленные здесь планы не являются подтверждением работоспособности API.

В трекере у каждой задачи: исполнитель, принимающий, зависимости, ссылка на PR/отчёт, статус, замечания и подтверждение с датой. GitHub Issues/Projects или Notion достаточно; отдельная система управления разработкой не нужна.

## Что передавать на каждую проверку

- Ссылка на PR или отчёт и короткое описание наблюдаемого результата.
- Какие ID методов из реестра затронуты; ссылка на обновлённый контракт.
- Как воспроизвести проверку на тестовых данных: конкретные действия, ожидаемый и фактический результат. Если нужны команды — отдельным блоком, без секретов.
- Результаты автоматических тестов, включая отрицательный сценарий, и подтверждение, что действующие тесты проходят.
- Известные ограничения, влияние на конфиг/схему БД, способ отката. Непроверенные свойства явно отмечаются.

Для исследовательской задачи вместо кода — протокол эксперимента, безопасные примеры, источник и вывод с уверенностью. Для задачи реализации — работающий код, тесты и документация, а не только описание намерений.

Шаблон подтверждения для reviewer:

```text
Задача: <ID>
Результат: Принято / На доработку / Заблокировано
Проверено: <сценарии и ссылка на доказательства>
Замечания или принятые ограничения: <текст>
Разрешено начать: <ID следующей задачи либо «нет»>
Проверяющий и дата: <имя, дата>
```

## Этап 0. Проверенный контракт — точка G0

| Задача | Что сделать и передать | Проверяющий принимает, если |
|---|---|---|
| 0.1. Сверить всю API-поверхность | Актуализировать подготовленные 64 операции; разрешить отсутствующие в оглавлении методы и спорные пути; начать матрицу полей/ответов | У каждого метода есть источник, ожидаемая функция и явный статус проверки; неизвестные методы не спрятаны |
| 0.2. Проверить подключение и квоты | Протокол тестового входа, token/logout, HTTP/body ошибок, рабочего host, IP и лимитов | Утверждён рабочий endpoint; понятно, как сервис входит и ограничивает суммарный поток; неподтверждённые границы помечены |
| 0.3. Доказать изоляцию сложных объектов | Сохранить live-протокол; оформить первоначальное предложение scope и безопасные правила C05, C06–C07, L01/L06, T02–T03 | PM/архитектор письменно принял безопасные правила: без доказанной принадлежности операция не выполняется и данные не выдаются; для принятых в v1 методов соответствующие проверки изоляции обязательны при реализации. Все 64 ID классифицированы без пересечений и факты отделены от предложения. Итоговый scope фиксирует 0.5 |
| 0.4. Проверить события и медиа | Примеры обеих callback-схем, способ проверки источника, правила подписок, получение записи/файла через сервер | Понятны доверие к событию, обработка удаления и рабочая схема media; нет недоказанного обещания подписи/доставки |
| 0.5. Зафиксировать контракт и объём | Зафиксировать согласованный архитектором scope 52/12, условия возврата, deferred callback, нейтральный `501` и открытое расхождение `400/404` против текущего `422` | PM отдельно принимает либо отклоняет пакет `docs/decisions/001-v1-scope-contract.md`; решение синхронно отражено в реестре, матрице, плане, задачах, валидируемом `docs/api/openapi.yaml` и `docs/api/client-contract.md`. Приёмка 0.5 не заменяет отдельный G0 |

**G0:** отдельная отметка о реализуемости принятого в 0.5 объёма и отличиях. Scope 52/12 согласован архитектором, но ещё требует PM-приёмки; G0 не следует автоматически из этого согласования. Перед G0 должны быть синхронны условия возврата deferred, фиксированный контракт `501`, безопасные правила v1 и перечисленные артефакты. Порядок остаётся `0.3 → 0.4 → 0.5 → G0 → 1.1`.

Письменная форма D01–D10, решения по блокерам 0.4 и оценка находятся в [Decision 001](../decisions/001-v1-scope-contract.md). Статус документа фиксирует согласование архитектора, но PM-приёмка и G0 ещё не выполнены.

### Согласованный архитектором пакет изменений 0.5

Ниже перечислен единый change set для отдельной PM-приёмки. Он не является отметкой `0.5 ACCEPTED` или `G0 APPROVED`.

- `2.1`: нейтральный отказ для detail без доверенной mapping и очистка nested staff в `T02–T03`;
- `2.2`: для `C06–C07` использовать только доверенную server-side связь `detail → contact → project` и повторную проверку родителя; без доказанной связи отказать нейтрально до upstream-вызова;
- `2.3`: отсутствие публичного `S01` в v1 и запрет использовать account-scoped staff как доказательство project membership;
- `3.2`: `C08` исключён из v1, `C05` требует project precheck и отдельного теста каскада;
- `3.3`: `L11` исключён, а `L01/L06` не принимают неподтверждённые owner/observers;
- `4.2`: в v1 остаются только `T02–T03`; `T01/T04/T05` возвращаются после выполнения зафиксированных условий;
- `5.1`: оставить L09; L10 перевести в deferred;
- `5.2`: исключить `L22` из v1 до доказанной project-scoped семантики и зафиксировать условие возврата;
- `5.3`: оставить L08/L21, выдавать L21 только через безопасный домен ProxyAPI, callback не реализовывать;
- этап 6: отложить P05–P08 и доставку callback; callback не входит в 64 операции;
- `7.1`: contract/e2e coverage для 52 v1 и одинаковый нейтральный отказ для 12 deferred без object lookup, LPTracker-вызова и внутреннего login;
- завершение этапа 0 и G0: провести отдельную PM-приёмку, затем отдельный G0;
- G7: 52 реализованных метода и 12 проверенных neutral refusals; открытый security-дефект блокирует точку;
- оценка архитектора `36–57` человеко-дней относится к полному объёму, включая уже принятые задачи, и не является оставшимся сроком.

## Этап 1. Клиент видит свой проект — точка G1

| Задача | Что сделать и передать | Проверяющий принимает, если |
|---|---|---|
| 1.1. Подготовить окружение | Запуск backend/БД/Redis, миграции, CI, безопасная конфигурация, нейтральный healthcheck | Проект запускается из чистого окружения; тесты выполняются; в репозитории/логах нет секретов |
| 1.2. Ручной конфиг и наша авторизация | Валидация YAML, password hashing, наши login/logout/token, отзыв, применение ревизии | Вход работает без обращения в LPTracker; плохой конфиг не применяется; credentials и token клиента не уходят наружу |
| 1.3. Внутреннее подключение | Адаптер с собственным login, token manager, квотой, deadline и безопасными ошибками | Два процесса соблюдают общий лимит; один refresh не порождает множество логинов; секреты закрыты |
| 1.4. Сквозной список проектов | P01–P02 через полный путь, два клиента/два проекта | Каждый получает ровно один проект; чужой ID отвергается; logout первого не мешает второму |

**G1:** reviewer самостоятельно воспроизводит «ручная запись клиента → login → один проект → logout». Это первый работающий вертикальный результат, но ещё не готовность всего сервиса.

## Этап 2. Общая защита объектов — точка G2

| Задача | Что сделать и передать | Проверяющий принимает, если |
|---|---|---|
| 2.1. Чтения с доказанным проектом | Проверки контакта/лида/просмотра/задачи, проектных списков и всех мест project_id | Негативные ID и конфликтующие query/body не раскрывают данные; объект без доказанного проекта не выдаётся |
| 2.2. Индекс contact details | Доверенная server-side связь `detail → contact → project`, обновление связи и повторная проверка родителя для C06–C07 | Клиент не может подделать связь; объект без доказанной связи получает нейтральный отказ до upstream-вызова |
| 2.3. Справочники и сотрудники | Поля, шаги, метки, staff, нейтральный owner=0 и очистка вложенных профилей | Нельзя получить чужой проект/профиль; все нужные связи доступны для проверки будущих записей |
| 2.4. Проверить общий модуль доступа | Набор атакующих тестов для реализованных чтений, кэшей, конфига и изменения прав | Все отрицательные сценарии проходят; reviewer согласен, что записи будут использовать этот модуль без обходных путей |

**G2:** reviewer принимает схему принадлежности для каждого типа ID из реестра. Дальнейшие записи используют только принятые проверки.

## Этап 3. Контакты, лиды и просмотры — точка G3

| Задача | Что сделать и передать | Проверяющий принимает, если |
|---|---|---|
| 3.1. Журнал и безопасная первая запись | Реализовать создание контакта вместе с состояниями операции, Idempotency-Key и timeout после отправки | Один ключ не создаёт два контакта; авария после отправки остаётся unknown; клиент видит request ID |
| 3.2. Группа контактов v1 | C01–C07, C09–C12; C08 — фиксированный deferred-отказ | Совместимость полей и clear_contacts подтверждена; C08 возвращает `501` без object lookup/upstream; ни одна запись/очистка не проходит с чужим ID |
| 3.3. Основные операции лидов | Создание/чтение/список/изменение/удаление, шаг и owner, проверки вложенного контакта | Сквозной жизненный цикл работает; чужой контакт/шаг/owner блокируется до записи |
| 3.4. Поля, комментарии и платежи | Создание полей/категорий, значения, очистка, комментарии, платежи | Поддерживаются типы и побочные изменения; timeout не приводит к повторному платежу/комментарию |
| 3.5. Просмотры и связи | V01–V04 и работа view/view_id в лидах | Проект просмотра проверяется отдельно; чужой view не привязывается к своему лиду |

**G3:** показать полный цикл контакта/лида/просмотра и ошибки записи. Пока не реализованные звонки, файлы и события явно отмечены в реестре, а не пропускаются сырым proxy.

## Этап 4. Остальные сущности и настройки — точка G4

| Задача | Что сделать и передать | Проверяющий принимает, если |
|---|---|---|
| 4.1. Метки | M01–M04, проверка по проектному списку | Чужую метку нельзя изменить/удалить/использовать; формат ответа подтверждён |
| 4.2. Задачи | T02–T03; T01/T04/T05 — фиксированный deferred-отказ | T02–T03 проверяют проект и очищают nested staff; deferred возвращают `501` без object lookup/upstream |
| 4.3. Настройки и автоворонки | P09–P14 и связанные чтения, проверка побочных эффектов | Меняется только назначенный проект; состояние и ошибки соответствуют контракту |

**G4:** все настройки и новые сущности прошли сценарии двух клиентов; общий аккаунт не создаёт недокументированный общий доступ.

## Этап 5. Файлы, сообщения и телефония — точка G5

| Задача | Что сделать и передать | Проверяющий принимает, если |
|---|---|---|
| 5.1. Файлы | L09; L10 — фиксированный deferred-отказ | Загрузка L09 контролирует проект, размер и MIME; L10 возвращает `501` без object lookup/upstream |
| 5.2. Сообщения и история | L19–L20; L22 — фиксированный deferred-отказ | Сообщения и вложения совместимы; повтор при неизвестном исходе не отправляется автоматически; L22 не вызывает upstream |
| 5.3. Звонки и media | L08, L21, собственный media endpoint, Range и подписанные ссылки; без callback | Тестовый звонок один; запись проигрывается только с безопасного домена ProxyAPI; чужая/отозванная ссылка не выдаёт запись |

**G5:** в доступных клиенту служебных данных и сетевом пути получения медиа нет прямого обращения к инфраструктуре LPTracker. Произвольный контент файлов не считается гарантированно очищенным.

## Этап 6. Вебхуки — deferred

P05–P08 и доставка callback не реализуются в v1. P05–P08 после успешной локальной авторизации возвращают фиксированный `501` без проверки объекта и без LPTracker-вызова, включая внутренний login. Доставка callback остаётся отдельной deferred-возможностью вне 64 операций. Точка G6 переносится вместе с возвратом этого scope.

## Этап 7. Полное покрытие и эксплуатация — точка G7

| Задача | Что сделать и передать | Проверяющий принимает, если |
|---|---|---|
| 7.1. Закрыть реестр контрактными тестами | Отчёт по всем 64 строкам: success/error/isolation/field tests для 52 v1 и единый neutral-refusal test для 12 deferred | Все 52 v1 покрыты; все 12 deferred возвращают HTTP 200 + application `501` с точным сообщением без object lookup/upstream/internal login; DOC/LIVE-факты не подменены |
| 7.2. Отказы, квоты и утечки | Общие сценарии из основного плана, несколько процессов, падения зависимостей, unknown, SSRF и секреты-маркеры | Изоляция и лимиты не обходятся при отказах; сырой upstream не выдаётся |
| 7.3. Эксплуатация и независимое review | Метрики/алерты, runbook, backup/restore, отзыв, конфиг rollback, review доступа и повторов | Другой специалист проверил критические участки; восстановление не возрождает отозванные права и не дублирует записи |

**G7:** техническое разрешение на пилот для 52/12. Открытые дефекты изоляции, утечки, повторного действия, непокрытый v1-метод или неверный deferred-отказ блокируют эту точку. Доставка callback не считается реализованной.

## Этап 8. Пилот и итоговая сдача — точка G8

| Задача | Что сделать и передать | Проверяющий принимает, если |
|---|---|---|
| 8.1. Пилотная самописная CRM | E2E сценарии, нагрузка, файлы/звонки/события, фактические отличия, проверка отката | Заказчик подтверждает работу интеграции через наш домен и приемлемость согласованных отличий |
| 8.2. Передача и второй клиент | Финальный комплект, инструкции, создание второго клиента только конфигом | Эксплуатация повторяет подключение/отзыв без изменения кода, а заказчик подписывает итоговую приёмку |

**G8:** результат принят заказчиком. Только после этого выполненной считается вся задача, а не отдельный сквозной пример.

## Как вести ход работ

Создать задачи в выбранном трекере с явной зависимостью от предыдущей и контрольной точки этапа. Не менять критерии задним числом для получения статуса «Принята». Если фактический API требует другого решения, записать отклонение в `proxy-api-implementation-plan.notes.md`, приложить доказательства и получить подтверждение нового критерия до завершения задачи.

Проверяющий заранее согласует срок ответа на ревью. В оценках основного плана время ожидания подтверждений не учтено; последовательные контрольные точки и доступность reviewer влияют на календарный срок. Исполнитель может подготовить описание следующей задачи, но её код до явного разрешения не пишет.
